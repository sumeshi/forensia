# 調査履歴の共有

## 目的

別の仮説や以前のセッションで得た検索経験を、小型のローカルLLMが次の検索計画へ利用できるようにする。最終的なFindingへ採用されなかった観測や失敗も、既存のCase / Traceから見つけられることを重視する。

調査状態の正本はケースのDuckDBである。履歴用の独立DB、モデルが維持する記憶文書、別の計画ループは追加しない。

## 公開資料から確認した設計

- [Autumn-27によるARTEX紹介](https://github.com/ruanyf/weekly/issues/10911)（2026-07-28公開）では、Plannerがグラフの構造化概要を読み、必要なWorkの実行過程を詳細取得する構成が説明されている。実行時の観測をエージェントから検索できるデータとして保存し、現在の作業以外でも利用することが明記されている。これは開発者の設計説明であり、FORENSIAでの効果を測った資料ではない。
- 同投稿には、目標と対象に結び付いたカバレッジ、複数の探索経路の維持、重要な発見に対する対抗的な再確認も説明されている。これらは次の検討対象である。取得した証拠のCoverage、調べた範囲、結論に必要な十分性は、フォレンジックでは区別する必要がある。
- [ARTEX Globalのツール名不一致の報告](https://github.com/jiwoochris/artex-global/issues/19)（2026-10-10公開）には、投稿者の実行で279呼出し中141件が拒否されたという集計がある。こちらで再現した数値ではない。ツールの名称と実行契約を明確にし、失敗を分類して復旧を有限にする重要性を示す事例として参照する。
- [Evidence assuranceとcoverage provenanceの議論](https://github.com/jiwoochris/artex-global/issues/47)（2026-10-18 JST公開）は、証拠に基づく検証と探索済み範囲を区別する提案であり、性能改善を確認した報告ではない。FORENSIAでは既存のAssessment / Sufficiency / Settlementに責務を保つ。
- [FORENSIA開発者の記事](https://sumeshi.github.io/posts/works/do-localllms-dream-of-forensic-investigator-2)の、ローカル完結、限定されたモデル能力、長時間調査でも一貫性を維持する方針に合わせる。

## 現在の構成

`investigation.trace_history`は、`trace.investigation_steps`の実行・評価記録から履歴を読み取る。モデルから永続状態を追加生成せず、既存のReceiptと元の仮説を参照する。

1. 現在の対象・検証条件・説明から検索語を組み立て、他の仮説の関連試行を検索する。Unicodeの文字を検索語として扱う。
2. 現在の作業の証拠テーブルに適合する履歴を、安定した参照とともに少数選ぶ。短いquery IDはセッションをまたいで重複し得るため、Receipt / Stepの参照を使う。
3. 選んだ概要のうち、少数の試行だけ詳細を読み取る。検索内容、実行状態、返却件数、根拠ID等を限定して提示する。
4. 通常のquery plannerへ追加の文脈として渡す。モデル呼出しや出力actionの種類は増やさず、生成した検索は現在の許可範囲・SQL検証を通す。

初期の選択方針はホストによる決定論的な検索である。概要検索と詳細取得の関数を分けることで、今後の選択方針を同じ保存契約の上で比較できる。現在の仮説自身の直近履歴は、既存の`PRIOR_ATTEMPTS`が扱う。

## 信頼と予算の境界

過去の実行記録は、当時何を試したかを示す。現在の仮説を支持する証拠とは扱わない。

- 原本の範囲、元のVerificationSpec、証拠内容の現行性を個別に確認する。識別情報を持たない古い記録は不明として扱う。
- 生の例外本文、モデルによる判定・要約を他の仮説へ渡さない。履歴内の文字列はデータとしてエスケープする。
- 検索結果が0件であっても、現在の対象の不存在を証明しない。検索結果や判定を自動的に再利用せず、現在の検証条件で評価する。
- 概要・詳細・SQL・証拠IDには上限を設ける。長いSQLを途中まで切って実行可能な全文として表示しない。
- `CASE_ATTEMPT_HISTORY`は省略可能な文脈である。入力予算を超えた場合はブロック全体を除き、現在のTaskと証拠を保持する。
- 採用した履歴の参照と文字数を既存のretrieval telemetryに記録する。prompt作成時の選択とproviderへ送る前の省略を区別する。

## 検証と次の採用判断

回帰テストでは、別仮説・別セッションの履歴への到達、無関係な履歴の除外、古い根拠の識別、件数・文脈予算、現在の判定を変更しないこと、通常のSQL検証経路を確認する。

これらのテストは保存・検索・境界の成立を確認する。実際の調査での正答率、重複検索、token、時間の改善は、同じ証拠revision・モデル・予算を使う比較調査で測る必要がある。

次の設計候補は、Taskの入力と完了条件、対象と調査範囲の関係、反証で競合説明を区別する作業選択である。既存の証拠評価と停止・再開の契約に接続し、一つずつ効果を比較する。

採用の優先度、既存実装との差分、実装時に保つ契約は[ARTEXの設計から採用するもの](artex-adoption.md)を参照する。
